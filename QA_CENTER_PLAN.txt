ENTREGABLE 2 — COMPARATIVA TÉCNICA DE PROVEEDORES
================================================================================

1. ASSEMBLYAI
───────────────────────────────────────────────────────────────────────────────
  Diarización:     ✅  speaker_labels: true → utterances[].speaker (A, B, C…)
  Timestamps:      ✅  word-level: words[].start / words[].end en ms
  Precisión:       ✅✅ Modelo "best" (universal-2) top-3 del mercado
  Latencia:        ~45–90s para 5 min (async)
  Costo/hora:      $0.37/hr (best) · $0.20/hr (nano)
  Integración:     REST API · SDK Node.js oficial
  Escalabilidad:   ✅  Cloud-hosted, 200 req concurrentes
  Pros:            Mejor diarización · Excelente español · SDK maduro
  Contras:         El más caro · API key adicional

  Respuesta:
  {
    "utterances": [
      { "speaker": "A", "text": "Buenas tardes…", "start": 0,    "end": 3200 },
      { "speaker": "B", "text": "Hola, estoy…",  "start": 3400, "end": 5800 }
    ]
  }


2. DEEPGRAM
───────────────────────────────────────────────────────────────────────────────
  Diarización:     ✅  diarize=true → words[].speaker (0, 1, 2…)
  Timestamps:      ✅  word-level: words[].start / words[].end en segundos (float)
  Precisión:       ✅✅ nova-3 — excelente en español
  Latencia:        ~20–40s para 5 min (más rápido que AssemblyAI)
  Costo/hora:      $0.26/hr (pre-recorded, nova-3)
  Integración:     REST API · SDK @deepgram/sdk para Node.js
  Escalabilidad:   ✅  Enterprise-grade, SLA disponible
  Pros:            30% más barato que AssemblyAI · Más rápido · SDK Node.js nativo
  Contras:         Diarización en dialectos regionales ligeramente inferior


3. GROQ (ACTUAL) + COMPLEMENTO LLM
───────────────────────────────────────────────────────────────────────────────
  Diarización:     ❌  whisper-large-v3-turbo no devuelve speaker labels
  Timestamps:      ⚠️  Solo segment-level con verbose_json (no word-level)
  Diarización alt: Post-procesar con LLaMA para etiquetar hablantes por patrones
  Precisión:       ⚠️  Baja — LLM puede inferir roles pero falla en turnos rápidos
  Latencia:        Groq muy rápido, pero 2 pasos (transcribe → diarize)
  Costo/hora:      ~$0.02/hr total (casi gratis)
  Integración:     ✅  Ya integrado — costo de cambio mínimo
  Escalabilidad:   ✅  Groq es muy escalable
  Pros:            Costo casi cero · Ya existe en el pipeline
  Contras:         Diarización no fiable · Sin word timestamps · No apto
                   para compliance real


4. OPEN-SOURCE (Pyannote + WhisperX)
───────────────────────────────────────────────────────────────────────────────
  Diarización:     ✅  pyannote/speaker-diarization-3.1 — state-of-the-art
  Timestamps:      ✅  word-level con WhisperX
  Precisión:       ✅✅ Comparable a AssemblyAI en condiciones controladas
  Latencia:        GPU: ~10s/5min · CPU: 2–5 min/5min
  Costo/hora:      $0.00 (self-hosted) · $0.05–0.10/hr (GPU cloud)
  Integración:     ❌  Requiere microservicio Python separado
  Escalabilidad:   ⚠️  Requiere gestión de infraestructura propia
  Pros:            Costo más bajo a escala · Control total · Sin vendor lock-in
  Contras:         Microservicio Python · GPU para latencia aceptable
                   No apto para Vercel serverless

ENTIDADES Y RELACIONES

  workspace_id (aislamiento multi-tenant absoluto)
       │
       ├──► qac_customers            ← identidad maestra del cliente
       │         │
       │         ├──► qac_call_threads        ← hilo de llamadas relacionadas
       │         │         │
       │         │         └──► qac_interactions (existente)
       │         │
       │         ├──► qac_customer_journey     ← estado del viaje del cliente
       │         │
       │         ├──► qac_follow_up_commitments ← compromisos hechos en llamadas
       │         │
       │         └──► qac_journey_insights     ← insights generados por IA
       │
       └──► qac_interactions (existente, FK customer_id)


TABLA: qac_customers
───────────────────────────────────────────────────────────────────────────────
  Propósito: Identidad consolidada del cliente. Un mismo cliente puede llamar
  varias veces desde distintos números o con distintos IDs externos.

  Columna            Tipo              Nullable  Descripción
  ─────────────────────────────────────────────────────────────────────────────
  id                 UUID PK           NO        Generado
  workspace_id       UUID FK           NO        Aislamiento tenant
  customer_phone     TEXT              YES       E.164 normalizado
  customer_id        TEXT              YES       ID externo del CRM
  name               TEXT              YES
  email              TEXT              YES
  first_call_at      TIMESTAMPTZ       YES
  last_call_at       TIMESTAMPTZ       YES
  total_calls        INT DEFAULT 0     NO
  is_merged          BOOLEAN DEFAULT F NO        Unificado con otro registro
  merged_into        UUID FK self       YES
  metadata           JSONB DEFAULT {}  NO
  created_at         TIMESTAMPTZ       NO        DEFAULT NOW()
  updated_at         TIMESTAMPTZ       NO        DEFAULT NOW()

  Índices:
  · UNIQUE (workspace_id, customer_phone) WHERE customer_phone IS NOT NULL
    AND is_merged = false
  · UNIQUE (workspace_id, customer_id) WHERE customer_id IS NOT NULL
    AND is_merged = false
  · GIN (to_tsvector('simple', coalesce(name, ''))) — búsqueda full-text

  Consultas frecuentes:
  · WHERE workspace_id = $1 AND customer_phone = $2  → buscar por teléfono
  · WHERE workspace_id = $1 AND customer_id = $2     → buscar por ID externo
  · ORDER BY last_call_at DESC                       → clientes más recientes


TABLA: qac_call_threads
───────────────────────────────────────────────────────────────────────────────
  Propósito: Agrupa llamadas relacionadas. Ej: todos los intentos de cobro de
  una deuda, o el proceso de venta de un producto a un cliente específico.

  Columna            Tipo              Nullable  Descripción
  ─────────────────────────────────────────────────────────────────────────────
  id                 UUID PK           NO
  workspace_id       UUID FK           NO
  customer_id        UUID FK           NO        → qac_customers
  campaign_id        UUID FK           YES       → campaigns
  thread_type        TEXT CHECK        NO        sales|collections|support|
                                                  onboarding|general
  status             TEXT CHECK        NO        active|resolved|abandoned|
                                                  converted
  opened_at          TIMESTAMPTZ       NO        DEFAULT NOW()
  closed_at          TIMESTAMPTZ       YES
  call_count         INT DEFAULT 0     NO
  last_call_at       TIMESTAMPTZ       YES
  resolution_notes   TEXT              YES
  metadata           JSONB DEFAULT {}  NO
  created_at         TIMESTAMPTZ       NO

  FK futura: qac_interactions.thread_id → qac_call_threads(id) (nullable)

  Índices:
  · (customer_id, created_at DESC)
  · (workspace_id, campaign_id, status)


TABLA: qac_customer_journey
───────────────────────────────────────────────────────────────────────────────
  Propósito: Estado actual del viaje del cliente. Un registro por
  cliente+campaña (upsert). Rastrear etapa del funnel, intent detectado,
  y trayectoria entre llamadas.

  Columna                   Tipo               Nullable  Descripción
  ─────────────────────────────────────────────────────────────────────────────
  id                        UUID PK            NO
  workspace_id              UUID FK            NO
  customer_id               UUID FK            NO        → qac_customers
  campaign_id               UUID FK            YES       → campaigns

  stage                     TEXT CHECK         NO        initial_contact |
                                                          interested |
                                                          objecting |
                                                          negotiating |
                                                          committed |
                                                          converted |
                                                          lost | churned |
                                                          reactivated
  previous_stage            TEXT               YES
  stage_changed_at          TIMESTAMPTZ        NO        DEFAULT NOW()

  current_intent            TEXT               YES       "quiere pagar en cuotas"
  intent_confidence         NUMERIC(4,3)       YES       0.000–1.000
  intent_history            JSONB DEFAULT []   NO        [{intent, at, call_id}]

  journey_score             NUMERIC(5,2)       YES       0–100
  intent_progression_score  NUMERIC(5,2)       YES       0–100
  relationship_score        NUMERIC(5,2)       YES       0–100

  known_objections          JSONB DEFAULT []   NO        objeciones expresadas
  expressed_interests       JSONB Default []   NO        intereses detectados
  risk_flags                JSONB Default []   NO        flags acumulados

  last_call_id              UUID FK            YES       → qac_interactions
  last_call_at              TIMESTAMPTZ        YES
  next_action               TEXT               YES       acción recomendada
  next_action_due_at        TIMESTAMPTZ        YES

  created_at                TIMESTAMPTZ        NO
  updated_at                TIMESTAMPTZ        NO

  Índices:
  · UNIQUE (workspace_id, customer_id, coalesce(campaign_id::text, 'null'))
  · (workspace_id, stage, last_call_at DESC)
  · (workspace_id, journey_score DESC NULLS LAST)

================================================================================
NUEVOS SCORES — DISEÑO (SIN IMPLEMENTAR)
================================================================================

1. JOURNEY SCORE (0–100)
───────────────────────────────────────────────────────────────────────────────
  Mide qué tan avanzado está el cliente en el proceso objetivo.

  journey_score = (
    stage_weight[stage]           × 0.40  -- etapa del funnel
    + intent_confidence           × 0.25  -- certeza del intent detectado
    + engagement_trend            × 0.20  -- tendencia engagement entre llamadas
    + commitment_fulfillment_rate × 0.15  -- % compromisos cumplidos
  )

  stage_weight:
    initial_contact = 10
    interested      = 30
    objecting       = 20  (retroceso temporal, no penalizar fuerte)
    negotiating     = 50
    committed       = 75
    converted       = 100
    lost / churned  = 0


2. FOLLOW-UP COMPLIANCE SCORE (0–100)
───────────────────────────────────────────────────────────────────────────────
  Mide qué tan bien el equipo cumple sus compromisos con el cliente.

  follow_up_score = (
    fulfilled_on_time / total_commitments_due × 100
  ) × decay_factor(days_late)

  Penalización por tardanza:
    0 días late  → × 1.0
    1 día late   → × 0.8
    2+ días late → × 0.5
    Never        → × 0.0

  Segmentado por: agent, campaign, workspace.


3. INTENT PROGRESSION SCORE (0–100)
───────────────────────────────────────────────────────────────────────────────
  Mide si el intent del cliente avanza hacia la conversión entre llamadas.

  intent_progression = direction_score × consistency_score

  direction_score:
    intent_history[n].stage > [n-1].stage → +20 por paso progresivo
    regresión                              → -15 por paso

  consistency_score:
    mismo intent 3+ llamadas seguidas → × 1.2 (señal sólida)
    intent cambia cada llamada         → × 0.7 (señal débil)


4. CONVERSION ATTRIBUTION SCORE (0–100)
───────────────────────────────────────────────────────────────────────────────
  Atribuye crédito de la conversión a los touchpoints correctos.
  Modelo: Time-Decay + Position weighting.

  Primera llamada:     20% del crédito
  Última llamada:      40% del crédito
  Llamadas intermedias: 40% restante con decay exponencial
                        (más reciente = más peso)

  quality_multiplier por llamada:
    overall_score >= 80    → × 1.3
    objection resolved     → × 1.2
    commitment extracted   → × 1.1


5. CUSTOMER RELATIONSHIP SCORE (0–100)
───────────────────────────────────────────────────────────────────────────────
  Score compuesto que resume la salud de la relación con el cliente.

  relationship_score = (
    journey_score              × 0.30
    + follow_up_compliance     × 0.25
    + intent_progression       × 0.20
    + avg_interaction_quality  × 0.15  -- promedio overall_score en llamadas
    + sentiment_trend          × 0.10  -- mejora de sentimiento 1ra vs última
  )

ESTRUCTURA diarized_transcript (JSONB)
───────────────────────────────────────────────────────────────────────────────

  {
    "provider":   "deepgram",
    "model":      "nova-3",
    "language":   "es",          -- idioma detectado o configurado
    "utterances": [
      {
        "speaker":       "0",      -- ID de hablante del proveedor ("0", "1"…)
        "speaker_type":  "unknown", -- "agent" | "customer" | "unknown"
        "text":          "Buenas tardes, mi nombre es Carlos…",
        "start_ms":      0,
        "end_ms":        3200,
        "confidence":    0.94
      },
      {
        "speaker":       "1",
        "speaker_type":  "unknown",
        "text":          "Hola, estoy llamando por mi cuenta.",
        "start_ms":      3400,
        "end_ms":        5800,
        "confidence":    0.91
      }
    ]
  }

  Nota sobre speaker_type:
  · Se almacena como "unknown" por defecto.
  · En llamadas inbound: Speaker 0 suele ser el cliente (quien llama primero),
    Speaker 1 suele ser el agente (quien responde).
  · En llamadas outbound: Speaker 0 suele ser el agente (quien origina).
  · Sin embargo, esto no es fiable sin más contexto, así que se deja "unknown"
    y se reserva la inferencia para Fase 2B cuando exista qac_customers.


TRANSCRIPT FORMATEADO PARA EL LLM (análisis)
───────────────────────────────────────────────────────────────────────────────

  Cuando diarized_transcript existe, el analysis engine construye este formato:

  Con 2 speakers (caso más común):
    "Speaker 0: Buenas tardes, mi nombre es Carlos, ¿en qué le puedo ayudar?
     Speaker 1: Hola, estoy llamando por mi cuenta.
     Speaker 0: Sí, dígame señor, ¿cuál es su consulta?"

  Con etiquetas inferidas (si direction = 'inbound' y 2 speakers):
    "Agent: Buenas tardes, mi nombre es Carlos, ¿en qué le puedo ayudar?
     Customer: Hola, estoy llamando por mi cuenta."

  NOTA: Se usa "Agent/Customer" solo si hay exactamente 2 hablantes detectados
  Y la dirección de la llamada es conocida. En cualquier otro caso → "Speaker N".

  Fallback (sin diarization, como hoy):
    Transcript plano sin etiquetas. El LLM recibe el texto tal cual.


LÓGICA DE TRANSCRIPCIÓN (webhook handler)
───────────────────────────────────────────────────────────────────────────────

  transcribeWithDiarization(recordingUrl, credentials, lang)
    │
    ├─ 1. Intentar Deepgram nova-3 (diarize=true, smart_format=true,
    │      punctuate=true, language=lang)
    │      ↓
    │      Respuesta OK
    │       → parsear utterances []
    │       → construir transcript plano (join de texts)
    │       → construir diarized_transcript JSONB
    │       → return { transcript, diarized_transcript }
    │      ↓
    │      Respuesta FAIL (timeout, 4xx, 5xx, clave ausente)
    │       → log error con código
    │       → FALLBACK ──►
    │
    └─ 2. Fallback: Groq Whisper (lógica actual sin cambios)
           ↓
           Respuesta OK
            → return { transcript, diarized_transcript: null }
           ↓
           Respuesta FAIL
            → return { transcript: null, diarized_transcript: null }

  En el INSERT a qac_interactions:
    · transcript: siempre el texto plano (de Deepgram o Groq)
    · diarized_transcript: JSONB si Deepgram OK, NULL si fallback

  INVARIANTE: transcript nunca es null si la transcripción tuvo éxito.
  El campo diarized_transcript es aditivo — null es válido y esperado.

PUNTO 2 — RELACIONES
───────────────────────────────────────────────────────────────────────────────

  workspaces
    │
    ├─ qac_customers (1:N)
    │    ├─ qac_call_threads (1:N) ← un cliente puede tener varios threads
    │    │    └─ qac_customer_journey (1:N) ← cada llamada del thread
    │    │         └─ qac_interactions (N:1) ← la llamada real
    │    ├─ qac_customer_journey (1:N) ← también directo (sin thread aún)
    │    ├─ qac_follow_up_commitments (1:N)
    │    └─ qac_journey_insights (1:N)
    │
    └─ qac_interactions (existente)
         └─ qac_customer_journey (1:1 max)  ← una llamada → un journey entry

  Regla: `qac_customer_journey.interaction_id` es UNIQUE
  → Una llamada pertenece a máximo un customer_journey entry
  → Un customer puede tener múltiples journey entries (múltiples llamadas)

PUNTO 4 — CUSTOMER IDENTITY RESOLUTION
───────────────────────────────────────────────────────────────────────────────

  Fuentes de identidad (en orden de confianza):

  1. customer_phone (extractor del webhook, normalizado E.164)
     → Fuente primaria. Más del 95% de las llamadas de call center tienen ANI.
     → Normalización: strip espacios, guiones, paréntesis; añadir country code
       si falta (configurable por workspace con un default_country_code).

  2. customer_email (si el webhook payload incluye el campo)
     → Fuente secundaria. Útil para omni-channel futuro.

  3. customer_name (campo existente en qac_interactions)
     → Fuente terciaria. Complementa display_name pero no identifica.

  Algoritmo de resolución:

  ┌─────────────────────────────────────────────────────────────────────────┐
  │  resolveOrCreateCustomer(workspaceId, phone?, email?, name?)           │
  │                                                                         │
  │  1. Si phone → normalizar a E.164                                       │
  │  2. Buscar qac_customers WHERE workspace_id=X AND canonical_phone=norm  │
  │  3. Si existe → retornar customer_id                                    │
  │  4. Si no existe → INSERT qac_customers                                 │
  │     · canonical_phone = normalizado                                     │
  │     · display_name = customer_name ?? "Unknown"                         │
  │  5. Si no hay phone pero hay email → mismo flujo con canonical_email    │
  │  6. Si ninguno → no se crea cliente (interaction queda sin customer_id) │
  └─────────────────────────────────────────────────────────────────────────┘

  Upsert atómico: INSERT ... ON CONFLICT (workspace_id, canonical_phone)
  DO UPDATE SET last_seen_at = now(), display_name = COALESCE(...) evita
  race conditions y duplicate entries.

  Casos edge:
  · Número con/sin prefijo internacional → normalización resuelve duplicados
  · Mismo cliente con phones diferentes (móvil + fijo) → puede generar 2
    clientes distintos. Fusión manual vía UI futura (fuera de Fase 2B).
  · Clientes sin phone (chat, email-only) → customer_id NULL permitido.


PUNTO 5 — AGRUPACIÓN DE LLAMADAS EN THREADS
───────────────────────────────────────────────────────────────────────────────

  Un thread representa un "caso" o "negociación" continua. No todas las
  llamadas de un cliente son el mismo thread (puede llamar por 2 temas
  distintos al mismo tiempo).

  Estrategia de agrupación (por prioridad):

  1. Thread_id explícito en webhook payload
     → Algunas plataformas (Genesys, Salesforce) envían un case_id.
     → Si el payload tiene call_thread_id o case_id, usar ese.

  2. Heurística temporal por intent
     → Si el customer ya tiene un thread OPEN y la última llamada fue hace
        menos de N días (configurable, default: 30 días), agrupar en ese
        thread SI el intent_at_call es compatible.
     → Si el intent cambia radicalmente → crear nuevo thread.

  3. Thread catch-all por defecto
     → Si no se puede determinar, agrupar en el thread OPEN más reciente
        del cliente. Si no hay ninguno → crear nuevo thread.

  Implementación:

  ┌─────────────────────────────────────────────────────────────────────────┐
  │  resolveOrCreateThread(workspaceId, customerId, callIntent?)           │
  │                                                                         │
  │  1. Buscar threads WHERE status='open' AND last_call_at > cutoff       │
  │  2. Si existe uno → retornar thread_id                                  │
  │  3. Si existen varios → seleccionar el más reciente                     │
  │  4. Si ninguno → INSERT nuevo thread con intent=callIntent              │
  └─────────────────────────────────────────────────────────────────────────┘

  El intent del thread se actualiza vía LLM en cada llamada analizada.
  El status se actualiza a 'resolved' cuando el call_outcome es 'resolved'
  o 'sold'.

PUNTO 7 — AISLAMIENTO CROSS-TENANT
───────────────────────────────────────────────────────────────────────────────

  Las 5 tablas nuevas replican el mismo patrón RLS de toda la plataforma:

  1. workspace_id NOT NULL en todas las tablas
     → Sin excepción. No existe fila sin workspace.

  2. RLS habilitado con 3 políticas por tabla:
     · SELECT: auth.uid() IN (SELECT user_id FROM workspace_members
                               WHERE workspace_id = t.workspace_id)
     · INSERT: misma condición
     · UPDATE: misma condición

  3. createAdminClient() (service role) solo en rutas del servidor
     → Nunca en client-side. Igual que todo el QAC actual.

  4. Consultas siempre filtradas por workspace_id
     → En resolveOrCreateCustomer: WHERE workspace_id = $ws AND ...
     → El customer de workspace A nunca es visible desde workspace B.

  5. canonical_phone es UNIQUE(workspace_id, canonical_phone)
     → El mismo número puede existir como clientes distintos en
        workspaces distintos. No hay cross-tenant leakage en identity.

  6. qac_call_threads.customer_id FK con workspace_id redundante
     → Permite queries eficientes sin JOINs innecesarios y elimina
        la posibilidad de que un thread de workspace A apunte a un
        customer de workspace B.

PUNTO 9 — RIESGOS
───────────────────────────────────────────────────────────────────────────────

  ┌──────────┬─────────────────────────────────────────────────────────────┐
  │ Nivel    │ Descripción y mitigación                                    │
  ├──────────┼─────────────────────────────────────────────────────────────┤
  │ ALTO     │ Phone normalization falla para números internacionales sin  │
  │          │ country code (p.ej. "0034..." vs "+34..."). Sin normaliza-  │
  │          │ ción consistente, el mismo cliente genera múltiples filas.  │
  │          │ Mitigación: usar librería phonenumber-js o validación E.164 │
  │          │ estricta; rechazar números no normalizables sin crash.       │
  ├──────────┼─────────────────────────────────────────────────────────────┤
  │ ALTO     │ resolveOrCreateCustomer() con race condition: dos webhooks  │
  │          │ simultáneos del mismo número pueden INSERT duplicado antes  │
  │          │ de que el UNIQUE constraint rechace el segundo.             │
  │          │ Mitigación: INSERT ... ON CONFLICT DO UPDATE (upsert        │
  │          │ atómico). PostgreSQL garantiza atomicidad.                  │
  ├──────────┼─────────────────────────────────────────────────────────────┤
  │ MEDIO    │ Thread grouping heurística puede agrupar calls no           │
  │          │ relacionados (p.ej. cliente llama por facturación y luego   │
  │          │ por soporte técnico, ambos en el mismo thread abierto).     │
  │          │ Mitigación: límite temporal configurable (default 30 días)  │
  │          │ + intent matching básico. Fusión/split manual en Fase 2C.   │
  ├──────────┼─────────────────────────────────────────────────────────────┤
  │ MEDIO    │ qac_follow_up_commitments requiere que el LLM detecte       │
  │          │ compromisos en el transcript. Falsos negativos son          │
  │          │ esperados (el LLM no detecta todos). No es bloqueante pero  │
  │          │ reduce el valor del Follow-Up Compliance Score.             │
  │          │ Mitigación: prompt dedicado, ejemplos few-shot.             │
  ├──────────┼─────────────────────────────────────────────────────────────┤
  │ MEDIO    │ ADD COLUMN customer_id en qac_interactions en migration 066 │
  │          │ es retroactivo solo parcialmente: llamadas históricas sin   │
  │          │ phone no se linkean a ningún cliente. El dashboard futuro   │
  │          │ debe manejar customer_id = NULL como caso normal.           │
  ├──────────┼─────────────────────────────────────────────────────────────┤
  │ BAJO     │ qac_journey_insights crece con cada análisis batch. Sin     │
  │          │ TTL o paginación puede convertirse en una tabla grande.     │
  │          │ Mitigación: expires_at column + job de limpieza futuro.     │
  ├──────────┼─────────────────────────────────────────────────────────────┤
  │ BAJO     │ DiarizedTranscript duplicada en dos archivos (riesgo ya     │
  │          │ documentado en Fase 2A). Al implementar lib/qac-customer.ts │
  │          │ se puede resolver moviendo tipos a lib/ compartido.         │
  └──────────┴─────────────────────────────────────────────────────────────┘
