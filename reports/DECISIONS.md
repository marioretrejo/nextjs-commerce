### Admin superadmin guard — centralized (Task 2)

The 16 `/api/admin/*` route handlers each re-implemented the same
"getUser → look up `is_superadmin` → 401/403" preamble in **four** subtly
different shapes (`guardSuperadmin` returning `admin|null`, `assertSuperadmin`
returning `user|null`, two `requireSuperadmin`s returning `{user,error}`,
plus fully inline copies). Some checked the profile via the RLS client, some
via the service-role client — the exact drift that turns a null profile row
into a 500 instead of a clean 403.

All 16 now use a single `requireSuperadmin()` from `lib/admin/guard.ts`, which
delegates the decision to the **pure**, unit-tested `evaluateSuperadmin(user,
profile)`. Null-safety (missing row / missing column / explicit false → 403;
no user → 401) is locked by `agent/tests/admin-guard.test.ts` (9 cases). The
guard short-circuits an unauthenticated caller **before** constructing the
service-role client, so a logged-out request gets 401 even where the
service-role credentials are absent.

**NOT done — `/api/admin` in middleware:** deliberately skipped. The middleware
`/admin` guard is a page-oriented `redirect('/dashboard')`; applying it to
`/api/admin/*` would answer an API call with a 302 to an HTML page instead of a
403 JSON. The in-route guards return the correct machine-readable status, so
they remain the authorization layer for the API surface.
